# 独立 GPT Image 2 生图站实施计划

## 1. 执行原则

本计划用于指导 AI 开发者按顺序实现一个独立静态生图网站。项目固定调用指定 Sub2API 后端，只支持 gpt-image-2 模型，不做用户系统，不做服务器图片存储，不接对象存储。所有图片历史和生成参数仅保存在用户浏览器本地。

执行时必须遵守以下规则：

- 严格按步骤顺序执行，不跳步。
- 每一步完成后必须执行该步骤的验证测试。
- 若某一步验证失败，先修复该步骤问题，再进入下一步。
- 不新增用户系统、服务端数据库、后端代理、对象存储或服务器本地图库。
- 不允许把生成图片上传到任何非 Sub2API 后端。
- 不允许把 API Key 发送到 Sub2API 以外的服务。
- 不提供可编辑模型选择器，所有图片请求固定使用 gpt-image-2。
- 大图只能保存到 IndexedDB，不允许保存到 localStorage。

## 2. 项目初始化

### Step 1: 创建前端项目骨架

目标：

创建一个独立静态前端项目，技术栈为 Vue 3、Vite、TypeScript 和 TailwindCSS。

操作指令：

- 在约定项目目录下初始化新的 Vue 3 + Vite + TypeScript 应用。
- 配置 TailwindCSS，使全局样式、响应式工具类和基础排版可用。
- 配置路径别名，保证后续模块导入路径稳定清晰。
- 删除默认示例页面、示例组件和无关资源。
- 建立基础目录结构，包括页面、组件、状态、服务、类型、本地存储、工具函数和测试目录。
- 设置应用标题从环境变量读取，默认标题为“GPT Image 2 生图站”。
- 保持项目为纯前端静态站，不引入服务端渲染框架。

验证测试：

- 执行依赖安装，确认无安装错误。
- 执行 TypeScript 类型检查，确认初始项目无类型错误。
- 执行生产构建，确认能生成静态产物。
- 启动本地开发服务，打开首页，确认没有默认示例内容残留。
- 检查产物中不存在服务端入口、API 路由、服务端数据库配置或对象存储配置。

### Step 2: 安装并约束项目依赖

目标：

安装 tech-stack.md 中推荐依赖，并避免引入不必要的大型框架。

操作指令：

- 安装 Pinia，用于全局状态管理。
- 安装 Dexie.js，用于 IndexedDB 封装。
- 安装 VueUse，用于轻量交互状态和浏览器能力封装。
- 安装 lucide-vue-next，用于按钮和操作图标。
- 安装 Vitest、Vue Test Utils 和 Playwright，用于单元、组件和浏览器验证。
- 不安装 Axios、大型 UI 组件库、Nuxt、Next.js、后端框架、服务端数据库客户端或对象存储 SDK。
- 在依赖清单中确认 Fetch API 作为唯一 HTTP 请求方式。

验证测试：

- 检查依赖清单，确认包含 Vue 3、Vite、TypeScript、TailwindCSS、Pinia、Dexie.js、VueUse、lucide-vue-next、Vitest、Vue Test Utils 和 Playwright。
- 检查依赖清单，确认不包含 Axios、Element Plus、Ant Design Vue、Nuxt、Next.js、Express、Koa、S3 SDK、OSS SDK、服务端数据库客户端。
- 执行依赖审计或等效检查，记录高风险依赖项；若存在阻断级风险，先替换或移除。
- 执行一次空测试套件，确认测试框架可启动。
- 执行生产构建，确认新增依赖没有破坏构建。

## 3. 配置系统

### Step 3: 建立环境变量配置

目标：

实现固定 Sub2API 后端地址和本地图库限制配置。

操作指令：

- 定义应用运行配置读取层，统一读取构建环境变量。
- 配置项必须包含 Sub2API Base URL、应用标题、本地历史最大数量、本地历史最大容量、是否允许记住 API Key。
- Sub2API Base URL 必须是必填项；缺失时应用应显示明确配置错误，而不是发送请求。
- 本地历史最大数量默认 50。
- 本地历史最大容量默认 5GiB。
- 是否允许记住 API Key 默认开启，但用户默认不勾选。
- 对 Base URL 做格式规范化，移除末尾斜杠。
- 不提供页面内 Base URL 输入框。

验证测试：

- 单元测试覆盖 Base URL 缺失时的配置错误状态。
- 单元测试覆盖 Base URL 末尾带斜杠时会被规范化。
- 单元测试覆盖历史数量和容量配置缺失时使用默认值。
- 单元测试覆盖非法容量配置会回退到默认值。
- 手动启动开发服务，确认页面显示的站点标题来自配置。
- 手动修改配置后重新构建，确认构建产物使用新的配置值。

### Step 4: 建立全局错误分类规则

目标：

统一处理认证、权限、余额、限流、CORS、网络失败、上游失败和本地存储失败。

操作指令：

- 定义错误分类模型，用于把请求失败转换为用户可理解的提示。
- 对认证失败显示“API Key 无效或已失效”。
- 对图片权限失败显示“当前 API Key 所属分组未启用图片生成权限”。
- 对余额或额度不足显示“余额或额度不足”。
- 对限流显示“请求过于频繁，请稍后重试”。
- 对 CORS 或预检失败显示“Sub2API 后端未允许当前生图站域名跨域访问”。
- 对网络失败显示“无法连接到 Sub2API 后端”。
- 对 IndexedDB 写入失败显示“图片已生成，但保存到本地历史失败，请立即下载”。
- 不把原始密钥、完整请求头或敏感响应内容写入错误日志或界面。

验证测试：

- 单元测试覆盖常见 HTTP 状态和错误体到用户提示的映射。
- 单元测试覆盖浏览器网络异常到 CORS/网络失败提示的映射。
- 单元测试确认错误提示中不会包含 API Key。
- 组件测试确认错误提示能在页面可见区域展示。
- 手动模拟错误 API Key，确认显示认证错误。
- 手动模拟无网络，确认显示连接失败或跨域配置提示。

## 4. API Key 与状态管理

### Step 5: 实现 API Key 状态管理

目标：

实现用户输入、显示隐藏、清除、会话保存和可选记住 API Key。

操作指令：

- 使用 Pinia 建立 API Key 状态模块。
- API Key 默认只保存到当前浏览器会话。
- 用户勾选“记住密钥”后才允许保存到 localStorage。
- 页面刷新后，如果用户未选择记住密钥，API Key 不应永久恢复。
- 页面刷新后，如果用户选择记住密钥，API Key 可恢复。
- 提供显示/隐藏密钥功能。
- 提供一键清除密钥功能，必须同时清除内存、sessionStorage 和 localStorage 中的密钥。
- API Key 不允许进入 IndexedDB 图库记录。

验证测试：

- 单元测试覆盖默认不持久化 API Key。
- 单元测试覆盖勾选记住密钥后可从 localStorage 恢复。
- 单元测试覆盖清除密钥会清空所有相关存储位置。
- 单元测试覆盖图库记录模型不包含 API Key 字段。
- 组件测试覆盖显示/隐藏密钥按钮状态。
- 手动刷新页面，分别验证记住和不记住两种行为。

### Step 6: 实现生成参数状态管理

目标：

管理 Prompt、尺寸、数量、质量、背景、输出格式、压缩比例、参考图、网页图片 URL、遮罩图等表单状态。

操作指令：

- 建立生成参数状态模块。
- Prompt 必填，提交前去除首尾空白。
- 尺寸提供 gpt-image-2 可用的固定选项，不允许自由输入非法尺寸。
- 数量限制为合理范围，并在界面中明确限制。
- 质量、背景、输出格式、压缩比例使用受控选项。
- 输出格式默认使用 webp 或 png，需保持与下载扩展名一致。
- response_format 固定为 b64_json，不展示给普通用户编辑。
- 模型固定为 gpt-image-2，内部请求构建时注入，不在状态中允许用户修改。
- 本地参考图、网页图片 URL 和遮罩图分别建模，避免互相覆盖。
- 支持一键重置参数到默认值。

验证测试：

- 单元测试覆盖 Prompt 为空时禁止提交。
- 单元测试覆盖模型始终固定为 gpt-image-2。
- 单元测试覆盖非法尺寸无法进入请求参数。
- 单元测试覆盖数量越界时会被阻止或回退。
- 组件测试覆盖重置参数后表单回到默认状态。
- 手动修改所有参数，确认页面状态和预期一致。

## 5. Sub2API 请求层

### Step 7: 实现文生图请求构建

目标：

构建 POST /v1/images/generations 的 JSON 请求。

操作指令：

- 建立图片 API 服务模块。
- 使用 Fetch API 发起请求。
- 请求地址由固定 Base URL 和 /v1/images/generations 拼接。
- 请求头必须包含 Authorization Bearer 用户 API Key。
- 请求体必须包含模型 gpt-image-2。
- 请求体必须包含 response_format b64_json。
- 仅提交用户在表单中启用或有值的参数，避免发送空字符串。
- 不允许请求中出现其他模型名。
- 处理非成功响应时交给全局错误分类规则。
- 成功响应必须解析出图片数组，支持多张图片。

验证测试：

- 单元测试确认请求 URL 正确。
- 单元测试确认 Authorization 头格式正确。
- 单元测试确认请求体固定包含 gpt-image-2。
- 单元测试确认请求体固定包含 b64_json 响应格式。
- 单元测试确认空可选项不会污染请求体。
- 单元测试确认多图响应能解析为多条图片结果。
- 使用模拟 Fetch 验证错误响应会进入错误分类流程。

### Step 8: 实现本地参考图改图请求

目标：

构建 POST /v1/images/edits 的 multipart/form-data 请求，用于上传本地参考图和可选遮罩图。

操作指令：

- 当用户上传本地参考图时，使用改图接口。
- multipart 请求必须包含模型 gpt-image-2。
- multipart 请求必须包含 Prompt。
- multipart 请求必须包含至少一张 image。
- 多参考图时使用 Sub2API 后端兼容的多 image 字段格式。
- 用户上传遮罩图时，附加 mask 字段。
- 自动携带尺寸、质量、背景、输出格式、压缩比例等适用参数。
- 不手动设置 multipart 边界，让浏览器自动生成。
- 上传前校验文件类型为图片。
- 上传前校验单张图片大小不超过前端限制，限制值需小于或等于 Sub2API 后端可接受范围。

验证测试：

- 单元测试确认无参考图时不会走 multipart 改图请求。
- 单元测试确认 multipart 请求包含模型、Prompt 和 image。
- 单元测试确认遮罩图存在时包含 mask。
- 单元测试确认非图片文件被拒绝。
- 单元测试确认超大图片被拒绝并显示提示。
- 使用模拟 Fetch 验证 multipart 请求不会手动设置错误的 Content-Type。
- 手动上传一张参考图，确认请求走 /v1/images/edits。

### Step 9: 实现网页图片 URL 改图请求

目标：

支持用户输入网页图片 URL，通过 JSON 调用 /v1/images/edits。

操作指令：

- 当用户未上传本地参考图但填写网页图片 URL 时，使用 JSON 改图请求。
- 请求地址为 /v1/images/edits。
- 请求体必须包含模型 gpt-image-2。
- 请求体必须包含 Prompt。
- 请求体必须包含 images 数组，每个元素包含 image_url。
- 支持多个网页图片 URL。
- 支持可选 mask.image_url。
- 对 URL 做基础格式校验，只允许 http 或 https。
- 网页图片 URL 和本地上传图片同时存在时，禁止混用并提示用户；用户必须二选一。

验证测试：

- 单元测试确认网页图片 URL 请求格式正确。
- 单元测试确认模型固定为 gpt-image-2。
- 单元测试确认非法 URL 被拒绝。
- 单元测试确认多个 URL 会进入 images 数组。
- 单元测试确认 mask URL 会进入 mask.image_url。
- 组件测试确认本地上传和网页 URL 冲突时有明确提示。
- 使用模拟 Fetch 验证请求发送到 /v1/images/edits。

### Step 10: 实现响应图片转换

目标：

把 Sub2API 返回的 b64_json 图片转换为浏览器可预览、可下载、可保存的 Blob。

操作指令：

- 解析响应中的每张图片结果。
- 支持 b64_json 字段。
- 如响应包含 revised_prompt，保存到结果元数据。
- 根据 output_format 或当前请求格式推断 MIME 类型。
- 把 base64 转换为 Blob。
- 为预览创建临时对象 URL。
- 在图片从结果区移除或页面销毁时释放临时对象 URL。
- 不把 base64 长字符串写入控制台。

验证测试：

- 单元测试覆盖 base64 到 Blob 的转换。
- 单元测试覆盖 MIME 类型推断。
- 单元测试覆盖多张图片转换。
- 单元测试确认 revised_prompt 能保存到元数据。
- 组件测试确认结果区能显示转换后的图片。
- 浏览器测试确认刷新前图片可预览、可下载。
- 内存检查确认删除结果后对象 URL 被释放。

## 6. IndexedDB 本地图库

### Step 11: 设计 IndexedDB 数据模型

目标：

设计只保存在浏览器本地的图库记录模型。

操作指令：

- 使用 Dexie.js 建立本地 IndexedDB 数据库。
- 建立图片历史表。
- 每条记录保存图片 Blob、缩略图 Blob、Prompt、生成参数、模型名、尺寸、质量、输出格式、生成时间、图片字节数、可选 revised_prompt。
- 每条记录必须有稳定本地 ID。
- 记录中不得包含 API Key、Authorization 头、Sub2API 账号信息或用户隐私标识。
- 提供数据库版本管理策略，支持未来迁移。
- 数据库名称使用项目专属名称，避免与其他应用冲突。

验证测试：

- 单元测试确认数据库可初始化。
- 单元测试确认写入记录后可读取完整字段。
- 单元测试确认记录中不存在 API Key 字段。
- 单元测试确认 Blob 字段能正确保存和读取。
- 单元测试确认数据库版本号存在且可识别。
- 手动在浏览器开发者工具中检查 IndexedDB 表结构。

### Step 12: 实现本地历史写入

目标：

生成成功后将图片和参数写入 IndexedDB。

操作指令：

- 每次生成成功后，为每张图片创建一条历史记录。
- 生成缩略图并保存，避免历史列表直接加载大图。
- 保存完整生成参数，支持后续重新载入参数。
- 保存创建时间，用于倒序展示和清理。
- 保存字节大小，用于容量控制。
- 写入失败时不影响当前结果预览，但必须提示用户立即下载。
- 写入过程不得阻塞图片预览渲染太久。

验证测试：

- 单元测试确认生成成功后写入历史。
- 单元测试确认多张图片生成会写入多条记录。
- 单元测试确认缩略图存在。
- 单元测试确认参数可完整恢复。
- 单元测试模拟 IndexedDB 写入失败，确认结果仍可预览且出现保存失败提示。
- 浏览器测试确认生成后历史列表出现新记录。

### Step 13: 实现历史读取、分页和排序

目标：

展示浏览器本地历史图库。

操作指令：

- 历史列表按创建时间倒序展示。
- 默认展示最近记录。
- 支持分页或增量加载，避免一次加载大量 Blob。
- 历史列表优先加载缩略图。
- 点击历史记录后可查看大图。
- 支持按 Prompt 文本进行本地搜索。
- 支持按生成日期进行本地筛选。
- 历史为空时显示空状态。

验证测试：

- 单元测试确认历史按时间倒序。
- 单元测试确认分页读取不会一次返回全部记录。
- 单元测试确认搜索 Prompt 能返回匹配记录。
- 单元测试确认日期筛选正确。
- 组件测试确认空状态显示。
- 浏览器测试确认大量历史记录下页面仍可滚动和操作。

### Step 14: 实现历史删除和清空

目标：

允许用户删除单条历史或清空全部本地历史。

操作指令：

- 每条历史记录提供删除操作。
- 删除前提示用户确认。
- 删除后从 IndexedDB 移除图片 Blob、缩略图和元数据。
- 清空全部历史前提示用户确认。
- 清空操作只影响 IndexedDB 图库，不影响 API Key 设置。
- 删除后释放当前页面中对应的对象 URL。

验证测试：

- 单元测试确认删除单条后无法再次读取。
- 单元测试确认清空后历史数量为零。
- 单元测试确认清空历史不会清除 API Key。
- 组件测试确认删除确认提示出现。
- 浏览器测试确认删除后历史 UI 立即更新。
- 浏览器测试确认清空后显示空状态。

### Step 15: 实现容量和数量自动清理

目标：

本地图库默认最多保存最近 50 张或 5GiB，超过后自动删除最旧记录。

操作指令：

- 每次写入历史后执行清理策略。
- 优先保留最新记录。
- 同时检查记录数量和估算总容量。
- 如果数量超过上限，删除最旧记录直到满足限制。
- 如果容量超过上限，删除最旧记录直到满足限制。

验证测试：

- 单元测试确认清理后总量满足限制。
- 浏览器测试确认连续生成超过限制后历史数量不超过配置。
